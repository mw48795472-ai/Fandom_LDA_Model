# Ad/Commercial Pilot — 정리 및 실제 데이터 병행 산출

## 이 문서가 다루는 것

"Ad/Commercial Pilot"(광고·상업성 지수)이라는 이름은 이번 세션이 새로 지은 것이 아니라, 저장소에
이미 남아있는 스크립트 한 개의 존재로부터 정리한 것이다.

- `scripts/indices_csv/build_ad_commercial_index_csv.py` — 주석에 "광고·상업성 지수(Ad/
  Commercial Index) 100개 팬덤 전체 CSV 산출"이라고 명시되어 있다. 입력은
  `/home/claude/work/data/ad_commercial_index_v7.json`인데, 이 경로는 이 프로젝트가 시작하기
  이전, 소실된 원본 작업 디렉터리를 가리키며 **이번 세션에는 존재하지 않는다.**

즉 Worldwide Language Pilot과 같은 상황이다 — 원본 산출 JSON과 정확한 서술은 이번 세션에 없지만,
그 지표가 정확히 무엇을 계산하려 했는지는 남아있는 스크립트의 컬럼 스키마로 알 수 있다. 다만
Worldwide Language Pilot과 달리, 이 스크립트는 **업종 목록(20개) 자체가 하드코딩돼 있지 않고
원본 JSON의 `industries` 필드에서 그대로 읽어오는 구조**라서, 20개 업종이 무엇이었는지는 스크립트
코드만으로는 전혀 복구할 수 없다(아래 "한계" 참고).

## 원본 스크립트가 정의하는 컬럼 스키마

```python
INDUSTRIES = data["industries"]      # 20개 업종, 원본 순서 유지 — 이번 세션에 없음
```

| 컬럼 | 정의 |
|---|---|
| 팬덤 | 팬덤명 |
| 구분 | 카테고리(`category`) |
| 근거문장수 | 전체 근거 문장 수(`n_total_bullets`) |
| 광고성문장수 | 광고·브랜드 관련으로 판정된 근거 문장 수(`n_ad_bullets`) |
| 광고비중 | 광고성문장수 ÷ 근거문장수(`ad_share`) |
| 대표업종 | 가장 많이 매칭된 업종(`top_industry`) |
| (20개 업종별 컬럼) | 업종별 매칭 건수(`industry_counts`) |

정렬 기준은 광고성문장수(`n_ad_bullets`) 내림차순이며, 스크립트 하단에 ① 광고성문장수 총합이
원본 JSON의 `total_ad_bullets`와 일치하는지, ② 업종별 합계가 원본의 `industry_totals`와
일치하는지 재검증하는 자체 무결성 체크가 있다(다른 지수 CSV 스크립트들과 동일한 패턴).

## 이번 세션에 실제로 있는 것 — 대체 가능한 실데이터

원본 20개 업종 세분류는 없지만, **이번 세션에 복구된 `data/v6_r22_snapshot/fandom_scores_v6.json`
안에 이미 개념적으로 가장 가까운 실수치가 들어있다.** 이 파일의 각 팬덤 레코드는 K=8/M=6 LDA
메타요인 분해 결과인 `factor_share` 딕셔너리를 갖고 있고, 그중 하나가 정확히 다음 라벨이다.

```
"브랜드·상업형(광고·앰버서더)"
```

`docs/LDA_V6_V7_TECHNICAL_SPECIFICATION.md`(4장, LABEL_RULES 표)에 이 메타요인(F2)의 정의가
그대로 남아있다.

| 코드 | 라벨 | 매칭 키워드 |
|---|---|---|
| F2 | 브랜드·상업형(광고·앰버서더) | 브랜드, 앰버서더, 발탁, 광고, 모델, 수상, 활동, 캠페인, 홍보대사, 음악 |

즉 원본 "Ad/Commercial Index"가 전용 20업종 분류기로 계산한 지표라면, 이번 세션이 가진 것은
**LDA 토픽모델링이 100개 팬덤 전체 코퍼스에서 자동으로 뽑아낸 6개 메타요인 중 하나로서, 같은
개념(광고·브랜드·앰버서더 성격)을 가리키는 독립적인 실측 대체 지표**다. 원본과 계산 방법 자체가
다르므로(수작업 업종 사전 매칭 vs LDA 비지도 토픽 분해) 수치가 같을 수는 없지만, "이 팬덤의
근거문장 중 광고·브랜드 성격이 얼마나 되는가"라는 같은 질문에 답한다는 점에서 유효한 병행
산출물이다.

## 이 문서와 함께 보는 파일

- `analysis/ad_commercial_pilot.ipynb` — `fandom_scores_v6.json`의 `factor_share` 무결성을
  재검증하고(6개 메타요인 비중 합 = 1.0), "브랜드·상업형(광고·앰버서더)" 비중을 원본 스키마의
  "광고비중"에 대응하는 값으로 취급해 100개 팬덤 전체를 순위화·분포 분석하는 노트북.
- `scripts/indices_csv/build_ad_commercial_index_csv.py` — 원본 스크립트(원본 JSON 없이는
  실행 불가, 컬럼 스키마 참고용으로 남겨둠).

## 한계 — 이번 파일럿이 재현하지 않는 것

1. **20개 업종 세분류가 무엇이었는지 전혀 복구되지 않는다.** 원본 스크립트가 업종 목록을
   하드코딩하지 않고 원본 JSON에서 그대로 읽어오는 구조라, 스크립트 코드만으로는 업종명
   자체를 하나도 알 수 없다(Worldwide Language Pilot의 14개 언어 코드처럼 스크립트에
   힌트가 남아있는 경우와 다르다).
2. **"광고성문장수"(정수 카운트)와 "광고비중"(비율)은 개념이 다르다.** 원본은 팬덤별 근거
   문장을 업종 키워드 사전으로 하나하나 매칭해 얻은 **정수 카운트 기반** 비율(`n_ad_bullets
   / n_total_bullets`)인 반면, 이번 세션의 `factor_share`는 LDA가 추정한 **연속적인 토픽
   혼합비중**이다. 실제로 `activity(근거문장수) × factor_share`를 계산해보면 정수에 가깝게
   맞아떨어지는 팬덤이 100개 중 8개뿐이라, 이 값을 "광고성문장수의 근사 정수 카운트"로
   되짚어 쓰는 것은 무리이며, 이 노트북은 그런 역산을 하지 않고 **비중(share) 그 자체**만
   비교 대상으로 삼는다.
3. **"대표업종"에 대응할 세부 정보가 없다.** `dominant_factor` 필드가 있긴 하지만, 이는
   6개 메타요인 중 가장 비중이 큰 것을 가리킬 뿐 20개 업종 중 하나를 가리키지 않는다 —
   실제로 100개 팬덤 중 `dominant_factor`가 "브랜드·상업형"인 경우는 1개(사이먼도미닉)뿐이라
   대부분의 팬덤에게는 이 메타요인이 "대표" 성격이 아니라 "구성 비중 중 하나"에 불과하다.
4. **코퍼스 규모 자체가 다르다.** round22 스냅샷은 100개 팬덤 5,612건 기준이고, 최종 v7
   리포트가 원래 어떤 코퍼스 규모(v7 몇 라운드)에서 Ad/Commercial Index를 산출했는지는
   기록이 남아있지 않다.
